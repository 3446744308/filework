# ADR-012: 上传会话磁盘持久化与下载会话续传口径

> Status: Accepted | Date: 2026-10-12 | Deciders: zwh | 关联 RFC: RFC-003 §4 | 影响：`server/sessions.js`、`server/transfer.js`、`server/store.js`、`server/index.js`、`web/src/api.js`、`web/src/downloader.js`、`web/src/pages/Upload.jsx`

## Context

RFC-001 把大文件传输改成"内存会话 + 分片"后，会话生命周期成了可靠性的短板（backlog B1-1）：

- **上传会话只存内存**，且启动时 `store.clearTmp()` **整目录清空** `data/tmp`——刷新丢 `uploadId`（客户端侧）、重启丢位图（服务端侧），只能整文件重传。
- **下载每次点击都新建会话并消费 1 次**：刷新或失败重试让用户为一个文件多付出下载配额；对 `maxDownloads` 敏感的分享这是真实损失。
- **明文密码驻留内存**：上传会话的 `fields.password` 一直保留到 `complete`；一旦为断点续传落盘，就会把明文带到磁盘。
- 匿名服务**没有用户身份**：恢复凭据不能依赖账号，只能依赖随机 bearer（`uploadId`/`token`）+ 客户端本地存储。

需要在"可恢复性"与"匿名服务的安全/资源边界"之间定几个口径：持久化什么、放哪里、密码怎么处理、续传能不能重复计限流/计数、TTL 是否滑动、下载要不要持久化。

## Decision

1. **上传会话以 `data/tmp/<uploadId>.json`（位图 + 元数据）为持久事实源**，`<uploadId>.bin` 为分片体；每次成功收片**原子更新** JSON（临时文件 + rename）。内存 Map 只是热缓存，磁盘才是可恢复状态。
2. **启动恢复取代整目录清空**：`store.clearTmp()` 删除，改为 `sessions.restoreUploadSessions(config.tmpDir)`——逐项校验（版本、未过期、数值字段、位图范围、`.bin` 存在）后恢复；不合法/过期/孤儿统一删除，保持"宁可再生，不冒用脏位图"的既有完整性红线。
3. **密码只以 SHA-256 出现**：`/api/upload/init` 即把 `password` 哈希后存入会话（内存 + JSON），`complete` 直接提交哈希；`store.commitUpload` 新增 `passwordHash` 入参（单次上传路径不变）。副作用是**内存中也不再驻留明文**，安全性好于改造前。
4. **恢复（`init` 带 `uploadId`）不重复计上传限流**：恢复是幂等只读语义，重复计费会让"刷新重试"反而触发 429；限流仍只对新会话计一次。下载侧同理：`GET /api/download/status` **不消费**下载次数（消费只发生在 `POST /api/download/session`，语义与 RFC-001 一致）。
5. **下载续传 = 会话续用（token 复用），不是字节续写**：浏览器刷新后内存缓冲/写盘管道已不可复用，`status` 返回原计划后依旧从分片 0 重新取；续传保证的是「配额不重复消耗 + 会话上下文（token/计划）延续 + 同页失败重试直接复用」。客户端 token 存 localStorage，**成功才 `end` 并清除记录**，失败保留至 TTL 由清扫器回收。真正的字节级续写（OPFS/FileSystemFileHandle 持久化）列为后续评估（backlog B4-10）。
6. **TTL 保持绝对过期**：上传 30 分钟（自创建）、下载 10 分钟（自创建），不滑动续期——匿名服务不能因续传被无限拉长会话生命周期；续传窗口 = TTL 内，超时按旧语义回退（新会话、重新消费）。
7. **下载会话不落盘**：内存 + 10 分钟 TTL 已覆盖"刷新/重试"场景；持久化会引入第二套生命周期与每下载一次的小写入，收益不足。
8. **客户端本地记录的最小化**：上传只存 `{ uploadId, filename, size }`（位图在服务端，随时 `status` 拉取）；下载只存 `{ token, filename, size }`；键分别按文件指纹与取件码，成功即删、失败保留。

## Alternatives

- **整目录持久化（把 tmp 定义为永久缓存，不清理）**：孤儿与过期文件无界增长，且与"tmp 是临时区"的运维预期冲突。否决。
- **把会话写入 `data/meta` 或独立数据库**：会话是高频小写、短生命周期数据，与分享元数据（消费语义核心）混放会重演 ADR-010 的耦合问题；SQLite 违背零依赖。否决。
- **下载也持久化会话**：换来的只是"服务重启后仍可续传"这一小概率场景，成本是每个下载一次额外写盘 + 第二套回收路径。否决（非目标）。
- **滑动 TTL**：长下载/长上传体验更好，但匿名服务会被单个客户端无限占用（位图与 tmp 空间），且让"过期清理"失去上界。否决（保持绝对 TTL，未来如有真实需求再评估）。
- **明文密码落盘（或干脆不持久化带密码的会话）**：前者不可接受；后者会让"带密码的断点续传"静默降级为"重传"。改为哈希落盘，两个问题同时解决。否决两者。
- **续传也计限流/消费次数**：实现最简单，但与"恢复"语义矛盾（刷新重试越试越糟）。否决。
- **客户端存位图（服务端无 JSON）**：客户端可伪造/漂移，服务端无法校验"分片确实收到"，`complete` 的完整性红线会受到影响。否决（服务端位图为事实源）。

## Consequences

- 正：上传刷新/重启后从缺口继续；下载重试/刷新不再重复消耗次数；明文密码不再驻留（内存与磁盘）。
- 正：位图随收片原子落盘，崩溃最多回退到"最后一次成功收片"，重传该片幂等覆盖；`restoreUploadSessions` 同时承担"tmp 卫生"职责（孤儿、过期、残留临时文件）。
- 负：单次分片上传多一次小 JSON 原子写（≤1024 片、每片数百字节）；`data/tmp` 在 TTL 内不再"随时可清空"，运维清空目录的语义变为"放弃未完成上传"（文档已登记）。
- 负/边界：下载续传不解决"刷新后已经下载的字节"（重新拉取）；token/位图是 bearer 凭据，`trust proxy` 场景下无额外绑定（匿名服务既有取舍，随机 192-bit/128-bit 不可猜）。
- 风险：位图 JSON 与 `.bin` 若被外部工具移动会失去一致性——恢复函数按"成对存在"校验并整对清理，只损失可恢复性，不产生错误数据。

## 修订记录

- 2026-10-12 修订一（backlog B4-10 / B4-4 的可行性实测）：决策 5（「下载也需要字节级续写」列为非目标）**保持不变，但实测已经完成，实施路线已明确**。实测环境：Windows / headless Chrome 154（CDP，`http://127.0.0.1` 安全上下文），临时探针跑完三阶段后已删除（结论可复现：OPFS 建文件 → 写 64KB 前缀 → 句柄存 IndexedDB → 刷新 → 浏览器完整重启）。结果：①`FileSystemFileHandle` 可 `structuredClone` 并存入/读回 IndexedDB（`roundTrip.isHandle = true`），`queryPermission({ mode: 'readwrite' })` 在刷新后与**浏览器重启后**均为 `granted`（无二次授权弹窗）；②刷新后沿用 `createWritable({ keepExistingData: true })` + `seek(已写偏移)` 续写，前缀/后缀逐字节完好且总长等于预期（65536 + 32768 = 98304）；③重启后句柄与文件同样完好可续写；④`navigator.storage.estimate()` 可用（实测 quota ≈ 10GB、usage 可分项看到 `fileSystem`/`indexedDB`）。**实施建议（待评审）**：不持久化用户的「另存为」句柄（`showSaveFilePicker` 必须用户手势、无法 headless 验证，且每次新会话可能需重新授权），而是下载先写 **OPFS 暂存文件**（句柄 + 已写偏移存 IndexedDB），完成后一次性导出到用户文件；该路线同时消掉 ADR-003 的 Blob 回退内存 O(文件大小) 问题（即 B4-4）。**尚未验证**：导出环节（用户文件对话框）需有头浏览器人工验收；OPFS 实际容量取决于磁盘剩余；多标签并发写同一暂存文件的互斥策略。验证证据与后续动作见 `docs/backlog.md` B4-10/B4-4。

- 2026-10-13 修订二（backlog B4-10/B4-4 落地，代码/测试 `b6eebf8`）：下载侧改为**字节级续写**，决策 5 的非目标项由此消解。实现（`web/src/downloader.js`）：
  - **落盘三态**：①手势期拿到用户句柄（`showSaveFilePicker`）⇒ 直接写用户句柄（不跨刷新续写）；②无句柄但有 OPFS（`navigator.storage.getDirectory`）⇒ 写 `fs-download-<code>.part`；③否则内存 Blob 拼装（非 Chromium 保留，风险如旧）。
  - **提交粒度**：每 4 个分片 `close()` 提交一次（不再逐片）。理由：`createWritable({ keepExistingData: true })` 的提交会把旧内容与新区间整体落盘，逐片提交在 E2E-3 的 14MB/16 片用例上实测多花约 0.6s（端到端 1554ms → 940ms，基线 1493ms），而批量提交仍保留「整片对齐」的续写粒度。
  - **续写判定**：暂存文件大小必须**正好等于前 k 个分片的字节和**（`stagedResume`）才续写第 k+1 片；不对齐或大于声明大小则丢弃重新写。因此不需要把已写偏移存 IndexedDB（文件长度即偏移），只需 `fs-download:<码>` 里的 token 仍可用。
  - **导出**：完成后用暂存文件的 `File` 对象建 blob URL 交给 `<a download>`（浏览器按需从盘读取，不整份进内存）；120s 后清暂存。
  - **多标签互斥**：`navigator.locks.request('fs-download-<码>', { ifAvailable: true })`，拿不到锁的标签回退内存 Blob（不另建会话、不重复消费）。
  - 验收：E2E-8 重写为「限速下载中 `Page.reload` 中断 → 刷新后续用同一 token，**只请求 12/16 片**（实测中断时已提交 1MB = 4 片）→ 落地文件 SHA-256 一致、`totalDownloads` 只 +1、暂存最终写满原始大小」。
  - 仍未验证（需人工/真机）：导出对话框（有头浏览器）、OPFS 容量上限（取决于磁盘剩余）、非 Chromium 真机峰值内存。
