# ADR-009: 统计写入批量聚合（合并读 + 阈值/定时刷盘）

> Status: Accepted | Date: 2026-10-12 | Deciders: zwh | 关联 RFC: RFC-002 §4.4 | 影响：`server/stats.js`、`server/index.js`、`scripts/test.js`

## Context

ADR-007 决策 2 把「原始字节 / 线上字节」两个基础计数落盘，代价是 **每次分片产出都做一次同步读-改-写** `stats.json`（tmp 文件 + `rename` 两次系统调用）。单文件分片数上限 `UNIT_MAX_COUNT=256`，即一次大文件下载最多 256 次同步写；并发取片（2~8 路）时这些写会与下载的数据读争抢磁盘 IO，也让 `stats.json` 的 inode 频繁更替（不利于任何外部读取者/备份）。backlog B4-7 记录了这个问题。

聚合写入的难点不在"少写"，而在两个语义不能被破坏：

- **读取必须始终最新**：管理端卡片、`/api/admin/stats`、测试都在传输结束后立刻读取，若必须等刷盘窗口，读数就会陈旧，测试也不得不靠 `sleep` 兜底（等于把不确定性写进测试）。
- **增量不能丢**：`recordUpload`/`recordDownload` 也是"读-改-写 `stats.json`"，若它们直接写文件而忽略内存里的传输增量，那批增量就被覆盖丢失（实现时必须先合并再落盘）。

## Decision

1. **内存聚合 + 合并读**：`recordTransfer()` 只累加模块级 `pending`（原始/线上字节 + 分片计数）；`readCounters()` 在返回前把 `pending` 合并进磁盘值。**读接口永远是"磁盘 + 未落盘增量"，因此不存在陈旧读**——调用方无需等待刷盘。
2. **两种刷盘触发**：
   - 阈值：`pendingParts >= FLUSH_PARTS(32)` 时立即刷盘一次（把长下载的写次数压到 `ceil(片数/32)` 量级）；
   - 定时：`setInterval(2s).unref()` 兜底，保证低流量下增量也在 2s 内落盘。
3. **`recordUpload`/`recordDownload` 先合并后写**：它们的读-改-写必须基于 `readCounters()`（含 `pending`），写完再清空 `pending`——把"增量可能被覆盖"这一坑固定在实现里，并由用例覆盖。
4. **优雅退出刷盘**：`flushCounters()` 导出，`server/index.js` 的 `shutdown()` 在 `SIGINT`/`SIGTERM` 时先刷盘再关闭，避免正常重启丢最后一个窗口。
5. **丢失窗口与口径**：崩溃/`SIGKILL` 时最多丢失一个刷盘窗口（≤2s 或 ≤31 片）的传输计数。计数是运维观测量、不是计费量，且丢的是"绝对值"而非比例口径，因此接受；`docs/DEVELOPMENT.md` §5 注明。

## Alternatives

- **继续每分片同步落盘（ADR-007 现状）**：语义最简单、零丢失窗口，但把磁盘写放大 256 倍于必要值，并在并发下载时与数据读争抢 IO。否决（改回）。
- **只改定时刷盘、读取仍读磁盘**：写变少了，但 `/api/admin/stats` 会滞后最多 2s，卡片与测试都要容忍陈旧读——把不确定性推给调用方与测试。否决。
- **写 WAL / 追加日志再合并**：能同时做到零丢失与少写，但引入文件生命周期（截断、损坏恢复）与新的读取路径，对一个运维计数器而言复杂度不成比例。否决。
- **`stats.json` 落 SQLite 或独立计数服务**：引入依赖与部署面（本项目坚持零依赖、单文件单例）。否决。
- **只在进程退出时刷盘**：写最少，但崩溃即丢整段（可能几十 MB 的统计），且外部读取者长时间看不到变化。否决。
- **把阈值/间隔做成 env**：本项目"新增 env 必须同步 `.env.example` + DEVELOPMENT §4"；两个常量没有现场调优的价值（CPU/IO 特性不因部署而异），先不引入配置面（若将来出现需求，按该流程补）。否决（本期）。

## Consequences

- 正：单次下载的同步写从"每分片一次"降到 `ceil(片数/32)`（实测：18 片的下载在接口侧立即可见、磁盘在 1250ms 内收敛，窗口内磁盘写 0 次、随后 1 次）。
- 正：读取语义不变——`/api/admin/stats` 与仪表盘卡片仍是即时准确值，既有断言（`scripts/test.js` [24]、`e2e-browser.js` E2E-6）无需 `sleep` 兜底即通过。
- 负：`stats.json` 与内存值可能短暂不一致（磁盘滞后），外部直接读文件者（如备份脚本）看到的是上一个窗口的值；读取一律走接口即可避免（已在 DEVELOPMENT §5 注明）。
- 负：崩溃丢一个窗口（≤2s 或 ≤31 片）的计数。以归档/备份为目的的读取应接受该误差。
- 风险：`pending` 是模块级内存态，多进程共享同一 `DATA_DIR` 时各自持有自己的增量、互相覆盖对方未落盘的增量（读-改-写竞争）。已在 dev 环境默认隔离数据目录（`scripts/dev.js` → `data-dev`），并要求生产只跑单进程。

## 修订一（2026-10-13，backlog B4-8）：可选 WAL 档位

决策 5 的「最多丢一个刷盘窗口」作为**默认行为保留**（`STATS_WAL=off`）；需要计费级精度时改为 `STATS_WAL=on`：

- 每次 `recordTransfer` 先追加一行 `{ o, w, c }` 到 `data/transfer-stats.wal`（`fs.appendFileSync`，同步顺序在内存累加**之前**，保证「日志有则内存必有」）。
- 启动 `replayWal()`：读 `stats.json.walOffset`（上次刷盘已消费的字节数）为水位线，只重放其后的记录；半截行（崩溃中断写入）解析失败即跳过。
- 刷盘时把 `walOffset` 更新为当前 WAL 文件大小——语义是「本次刷盘已包含日志的全部内容」，因此重放天然不重复；`resetTransferStats` 同样推进水位线，避免清零被重放回卷。
- 代价：每片多一次追加写（开启时）；关闭时零变化。验收：`scripts/test.js` [35]（隔离端口，`SIGKILL` 后重启零丢失 + 二次重启不重复累加）。
